# MCModSync 1.9.2 中文使用指南

本文是 README 的中文运维版，适合服主、整合包维护者和需要从 1.6.x/1.7 升级的管理员。当前公开版 `1.9.2` 要求 Java 21；同一个公开 JAR 同时支持 Fabric（Minecraft `1.21.1`、`1.21.11`）和 NeoForge 1.21.1。示例均使用占位域名；部署前必须换成自己控制的 HTTPS/HTTP 直链。

电脑端便携更新完成后，置顶窗口会显示“需要重新启动 / Restart Required”，并持续等待玩家点击“确定，返回启动器”，不会再于 5 秒后自动消失。手机端和无图形环境仍完全跳过 Swing 弹窗，只在日志与状态文件中提示重新启动。

> [!WARNING]
> 本项目包含 AI 辅助生成或修改的代码与文档。AI 代码没有经过你的环境安全审计。请在隔离实例验证、保留完整备份、扫描依赖并审阅清单和发布脚本。不要把账号、令牌、签名 URL、内网域名或个人路径提交到 GitHub。

## 一、先理解文件和启动流程

本地发布工作目录会生成两个清单：

```text
游戏根目录/
├─ modsync.properties       # 发布器模板，也是客户端本地配置
└─ mods/
   ├─ mods.txt              # 永久 v2 入口，只包含两个升级组件
   ├─ mods-v4.txt           # 正式 v4 清单，新版客户端使用
   ├─ MCModSync-Config.jar  # 固定名配置引导 JAR
   ├─ MCModSync-1.9.2.jar
   └─ 其他 Mod JAR
```

发布到服务器时推荐拆成旧地址与新版合并地址：

```text
https://old-pc.example.com/client/
├─ mods.txt
├─ MCModSync-Config.jar
└─ MCModSync-1.9.2.jar

https://old-mobile.example.com/client/
├─ mods.txt
├─ MCModSync-Config.jar
└─ MCModSync-1.9.2.jar

https://files.example.com/minecraft/merged/
├─ mods-v4.txt
├─ MCModSync-Config.jar
├─ MCModSync-1.9.2.jar
└─ 全部其他 JAR
```

清单 URL 的目录会作为 JAR 的相对下载目录。因此每个旧地址都要能下载当前同步器和配置引导 JAR；旧电脑和旧手机目录里的三个文件可以完全相同。中央合并目录保存完整 v4 清单和全部 JAR。旧客户端原来的 URL 必须继续返回 `mods.txt`，不要改成旧客户端不知道的新 URL。

启动器识别规则只有四个手机启动器：PojavLauncher、MCinaBox、FCL、Zalith Launcher 2。其余启动器按电脑端处理。

### 1.21.1 与 1.21.11 必须分开发布

公开版 `MCModSync-1.9.2.jar` 可以在 Fabric 的两个 Minecraft 版本和 NeoForge 1.21.1 中复用，但其他 Mod 通常不是同一个构建。服务器必须按 Minecraft 版本和加载器拆分：

```text
https://files.example.com/minecraft/1.21.1/fabric/
├─ mods.txt
├─ mods-v4.txt
├─ MCModSync-Config.jar
├─ MCModSync-1.9.2.jar
└─ 仅适用于 1.21.1 的其他 JAR

https://files.example.com/minecraft/1.21.11/fabric/
├─ mods.txt
├─ mods-v4.txt
├─ MCModSync-Config.jar
├─ MCModSync-1.9.2.jar
└─ 仅适用于 1.21.11 的其他 JAR
```

NeoForge 1.21.1 另用独立目录，例如 `https://files.example.com/minecraft/1.21.1/neoforge/`，其中的 `mods-v4.txt` 只能列 NeoForge Mod。Fabric 和 NeoForge JAR 不要混入一份清单；配置引导 JAR 已同时包含两套加载器元数据。主模组使用 `javafml` 的 `@Mod` 入口；配置引导包没有代码，NeoForge 侧使用 `lowcodefml`，不会要求不存在的入口类。

两套实例分别放置自己的 `modsync.properties`：

```properties
# Minecraft 1.21.1 实例
manifest=https://files.example.com/minecraft/1.21.1/fabric/mods-v4.txt

# Minecraft 1.21.11 实例
manifest=https://files.example.com/minecraft/1.21.11/fabric/mods-v4.txt
```

以下内容必须独立维护：URL 和目录、`modsync.properties`、永久 `mods.txt`、正式 `mods-v4.txt`、`catalog-version` 历史、MD5/SHA256、配置引导 JAR 以及全部目标版本 Mod。不要把两个版本的 JAR 混入一份清单，也不要让两个清单 URL 互相重定向；相同 Mod ID 的两个版本应分别出现在各自清单中。发布时只修改目标版本目录，先上传该目录的 JAR，再上传该版本的 `mods-v4.txt`，最后更新该版本的旧 `mods.txt` 入口。回滚也按版本单独执行。

旧 1.6.x/1.7 硬编码 URL 仍可保留，但每个旧 URL 必须归属于一个明确的 Minecraft 目标版本，并由其配置引导 JAR 写入对应版本的 v4 地址。不能把 1.21.11 旧客户端引导到 1.21.1 的普通模组清单，也不能反向操作。更完整的技术审计和验收表见 [`minecraft-1.21.1-1.21.11-parallel-update-audit.zh-CN.md`](minecraft-1.21.1-1.21.11-parallel-update-audit.zh-CN.md)。

### 1.21.11 私有迁移阻止版

停用旧 1.21.11 客户端时，可以把该实例中的普通同步器替换为私有迁移阻止版。此 JAR 只用于旧 1.21.11 客户端，不属于公开 1.9.2，不会上传 GitHub，也不要放入公开清单、公开源码包或 1.21.1 目录。它在 Fabric PreLaunch 阶段始终阻止 Minecraft 主类启动，显示中英双语“请更换为 Minecraft 1.21.1 客户端”提示，随后以退出码 `0` 正常结束。把 UTF-8 的 `migration-message.txt` 与私有 JAR、Mod 下载清单放在同一个云端目录；阻止版会从 `modsync.properties` 的 `manifest` 自动解析同目录 TXT，也支持 `-Dmcmodsync.migrationMessageUrl=...` 直接指定。TXT 最大 128 KiB，下载失败使用 JAR 内置副本。请通过私下渠道分发，并单独保存文件名、SHA256、部署范围和撤回记录。

## 二、必须模组和推荐模组

### 必须模组

必须模组在 Windows、Mac、Linux、手机端都强制存在。客户端检查文件名、Mod ID、MD5 和 SHA256；失败会自动下载或替换。清单不可用、下载失败、哈希错误或目录无法写入时，输出 `STARTUP_BLOCKED`，不运行 Minecraft 主类，并以退出码 `0` 正常结束。

### 推荐模组

电脑端首次遇到清单或 `catalog-version` 更新时显示选择窗口：

1. 所有兼容当前平台的推荐项默认勾选。
2. 云端标为“不兼容当前平台”的项自动取消并禁止勾选。
3. 每行必须/推荐二选一，不能同时勾选或全部不选类型。
4. 可一键取消所有推荐模组；全部不选仍允许启动。
5. 取消或关闭窗口按当前勾选继续下载，不会变成强制全选。
6. 取消已安装推荐 JAR 时移动到 `.modsync/backups`，不是永久删除。

手机端跳过窗口，自动下载本平台兼容的全部推荐项。同一个 `catalog-version` 只自动处理一次；之后用户删除推荐 JAR，日志提示手动 URL、SHA256 和目标目录，不会二次自动下载。清单版本更新会写入日志并开启新批次的一次自动处理。推荐项缺失不阻止启动，必须项仍会阻止。

## 三、准备客户端配置模板

把仓库根目录的 `modsync.properties.example` 复制到游戏根目录并改名为 `modsync.properties`。至少配置：

```properties
manifest=https://files.example.com/minecraft/merged/mods-v4.txt
syncResourcePacks=false
syncServerList=false
strict=true
requireManifest=true
```

`manifest` 必须指向 `mods-v4.txt`。本方案要把手机和电脑合并到同一地址，所以不要填写 `mobileManifest`；手机端未配置它时会自动使用 `manifest`。平台差异直接在同一份 v4 清单中用“不兼容的平台”标记。启用资源包或服务器列表同步时，分别填写对应清单 URL。

### 文件大小限制

默认不设置 Mod/资源文件大小上限。代码使用 `Long.MAX_VALUE` 作为未配置值，实际仍受磁盘、文件系统和 Java 可用内存/流的限制。只有本地配置显式写入：

```properties
maxFileBytes=2147483648
```

才启用约 2 GiB 的单文件限制。该项永远不会出现在 v4 清单、`client-config.*` 注释或 `MCModSync-Config.jar` 中，服务器无法远程覆盖。

## 四、使用图形发布器

在发布目录的 `mods` 文件夹放入当前同步器，然后运行：

```powershell
java -jar MCModSync-1.9.2.jar
```

选择 `mods` 目录并打开编辑器。发布器会先读取同级游戏根目录的 `modsync.properties`，验证 `manifest` 指向 `mods-v4.txt`，写入 `MCModSync-Config.jar`，再扫描当前同步器和其他 JAR。完整 v4 包含所有条目；永久 v2 只包含当前同步器和配置引导 JAR。

编辑步骤：

1. 想继续上次发布时勾选“扫描后选择上次清单”，选择任意位置的上次 v3/v4 文件。当前 `mods` 文件夹决定最终条目集合；删除的 JAR 不会保留。
2. 每一行用“必须 / Required”和“推荐 / Recommended”复选框选类型。勾选一侧会自动取消另一侧。
3. 推荐模组填写“不兼容的平台”：`Windows`、`Mac`、`Linux`、`手机`。默认四个平台全兼容，只有勾选的平台被排除。
4. 检查显示名称、版本、中文描述、English description。JAR 元数据通常只有一个描述字段，不要期待发布器自动翻译；从上次清单继续可保留人工填写的另一语言。
5. 每次推荐组合、平台兼容性、类型或描述有意义的变化都增加 `catalog-version`。
6. 生成后会得到完整 `mods-v4.txt`、只含两个升级组件的永久 `mods.txt` 和固定名 `MCModSync-Config.jar`。

按 Fabric 或 NeoForge Mod ID 合并时，旧清单中的类型、平台排除、名称和双语描述会保留；当前 JAR 的文件名、版本、MD5、SHA256 会刷新。无 Mod ID 时才退回文件名匹配。NeoForge-only JAR 的元数据来源是 `META-INF/neoforge.mods.toml` 的第一个 `[[mods]]` 表。

命令行模式适合自动化，全部条目默认为必须：

```powershell
java -jar MCModSync-1.9.2.jar "D:\Release\1.21.1\mods"
```

默认输出 `mods-v4.txt`，并在 `mods` 内输出 `mods.txt`。单独生成永久 v2 入口：

```powershell
java -jar MCModSync-1.9.2.jar --upgrade-v2 "D:\Release\1.21.1\mods"
```

## 五、从 1.6.x/1.7 升级

旧版不会读取 v4。不要更改玩家旧客户端中的硬编码 URL，也不要把 v2 内容放到 `mods-v4.txt`。发布器生成的永久 `mods.txt` 只把当前同步器和配置引导 JAR 列为必须模组；其他旧服务器管理模组先安全移出，新版再从中央合并 v4 地址重新下载。

上线顺序：

1. 在目标 Minecraft 版本目录上传 `mods-v4.txt`、`MCModSync-Config.jar`、`MCModSync-1.9.2.jar` 和该版本全部其他 JAR；建议先上传 JAR，最后上传清单。
2. 在属于同一 Minecraft 目标版本的原电脑地址和原手机地址各自上传同一份 `mods.txt`、`MCModSync-Config.jar`、`MCModSync-1.9.2.jar`。如果两个旧地址本来相同，只部署一份。
3. 保持旧客户端原有 URL 不变，并确认它仍返回 `mods.txt`。
4. 旧客户端启动一次：手机端自动把清单中不再列出的旧服务器管理模组移入 `.modsync/backups`；桌面端有窗口时会询问。随后按 `mcmodsync` Mod ID 替换同步器、安装配置引导 JAR，并以退出码 `0` 正常结束。
5. 再启动一次：1.9.2 从固定名 `mods/MCModSync-Config.jar` 自动创建/更新游戏根目录 `modsync.properties`，保留本地键，然后读取对应 Minecraft 版本的 `mods-v4.txt`。这里不配置 `mobileManifest`，所以同一目标版本的手机版与电脑端读取同一地址。
6. 新版从 v4 重建完整模组集：电脑端显示推荐选择；手机端自动处理本批次。存在下载/移动时再次以退出码 `0` 正常结束。
7. 下载完成后再启动一次，校验通过后进入游戏。

升级通常需要两至三次启动。旧模组是移动到备份，不是永久删除；中央 v4 会重新下载最终组合。`mods.txt` 不应删除，因为它是以后旧客户端升级的永久入口。

已经发布过含硬编码地址的 1.6.x/1.7 版本不需要玩家手工创建配置：只要每个旧地址仍返回永久 v2 `mods.txt`，引导 JAR 就会把发布模板中的合并 v4 URL 写入新客户端配置并持续更新服务器管理项。

## 六、远程配置白名单

v4 清单的头部可以包含：

```text
# client-config.manifest=https://files.example.com/minecraft/merged/mods-v4.txt
# 合并发布时不写 client-config.mobileManifest
# client-config.syncResourcePacks=false
# client-config.syncServerList=false
# client-config.strict=true
# client-config.requireManifest=true
```

允许的键只有：`manifest`、`mobileManifest`、`syncResourcePacks`、`resourcePackManifest`、`mobileResourcePackManifest`、`syncServerList`、`serverListManifest`、`strict`、`requireManifest`。`requireManifest=false`、未知键、非 HTTP/HTTPS URL 或把 manifest 指向非 `mods-v4.txt` 的文件都会被拒绝。

`language`、`connectTimeoutSeconds`、`requestTimeoutSeconds`、`fileOperationRetries` 和 `maxFileBytes` 属于客户端本地策略。远程清单更新时只更新白名单键，并原子写回配置文件；本地键保持不变。

`language=auto` 跟随 Windows/操作系统显示语言，不再读取 Minecraft `options.txt`。推荐选择窗口、同步提示、主要运行日志以及 `.modsync/helper.log`、`.modsync/progress.log`、`.modsync/ui-status.txt` 使用同一语言。需要固定语言时填 `language=zh_cn` 或 `language=en_us`；JVM 参数 `-Dmodsync.language=en_us` 的优先级最高。

## 七、版本更新和状态

以下变化应提高 `catalog-version`：推荐项增删、必须/推荐切换、不兼容平台改变、默认推荐组合改变或需要重新询问。电脑端会重新打开选择窗口；手机端获得新版本的一次自动处理机会。日志应类似：

```text
推荐清单版本更新: 2026-07-29-r1 -> 2026-07-30-r1
```

常用状态路径：

```text
.modsync/recommended-selection.properties
.modsync/server-manifest.txt
.modsync/backups/
.modsync/progress.log
.modsync/helper.log
.modsync/ui-status.txt
logs/latest.log
```

手机端删除推荐项后，请按日志手动下载并核对 SHA256；需要重新自动处理时发布新 `catalog-version`，不要让普通玩家随意删除状态文件。

若启动器控制台出现 `Could not find or load main class io.github.mcmodsync.PortableUpdateHelper`，先手动升级到当前 1.9.2（路径修复自 1.8.6 起包含）。真实故障包已证明 1.8.5 的辅助 JAR 完整、SHA256 正确且主类存在；故障位于该 Windows Java 环境解析/装载完整 `-cp` 启动路径的阶段，而不是 JAR 下载或内容，带分号的完整路径也已在回归测试中复现同类错误。1.8.6 起使用新的 `.modsync/helper-runtime-v2` 目录，以 `.part` 临时文件和原子移动生成副本，显式刷新时间戳并进行 MD5/SHA256 双校验；子 Java 以该目录为工作目录，只接收 ASCII JAR 文件名并通过 `-jar` 启动。父进程必须在 10 秒内收到 PID 匹配的 ready 信号才会正常退出；提前退出、PID 异常或超时会终止子进程、阻止本次启动并记录明确原因。升级前完全关闭该实例的 Minecraft/Java 进程；无需删除 `modsync.properties`、`mods.txt` 或推荐选择状态。

## 八、资源包、服务器列表和卸载

```powershell
java -jar MCModSync-1.9.2.jar --resourcepack "D:\Publish\server-pack.zip"
java -jar MCModSync-1.9.2.jar --serverlist "D:\Publish\servers.dat"
```

生成的清单和对应文件放在同一目录，在客户端配置中开启相应开关。发布时同样先上传文件再上传清单。

服务器列表使用独立所有权台账 `.modsync/server-list-managed-v1.dat`，具体规则如下：

1. 只有此前由 MCModSync 实际写入、并且还能与台账中的完整 NBT 条目唯一匹配的服务器，才属于可更新或可删除的云端管理项。
2. 玩家自行添加的服务器不按地址归云端所有。即使它和云端服务器使用相同地址，也不会被改名、覆盖或删除；玩家添加的重复地址也全部保留。
3. 云端管理项更新时保持它在本地列表中的原位置；云端移除时只拿掉这一项，不改变其他条目的相对顺序。
4. 本地尚不存在的云端新服务器追加到列表末尾。云端只调整排列顺序时，不得重排玩家当前列表。
5. 旧版本已有的 `.modsync/server-list-cloud.dat` 只是下载缓存，不会被当作所有权证据。升级到新版后，既有服务器默认全部按玩家条目保护；只有新版实际新增的条目才写入新台账。
6. 台账缺失、损坏、同一条目出现多个完整副本，或玩家修改了受管条目的名称、地址、图标等 NBT 内容时，客户端放弃该项管理权并原样保留，不会猜测删除。

请不要手工编辑所有权台账。误删台账不会删除服务器，但现有云端条目会转为受保护的本地条目，后续不能再由云端删除；需要重新纳管时应先由维护者确认并使用受控迁移工具，而不是直接复制旧云端缓存。

卸载：完全退出 Minecraft 和 Java，删除 `mods/MCModSync-1.9.2.jar`、`mods/MCModSync-Config.jar`，删除游戏根目录的 `modsync.properties`；如果使用 `-javaagent:`，从启动器 JVM 参数删除它。需要恢复被移出的推荐 JAR 时从 `.modsync/backups` 手动移回并核对哈希。卸载不会自动删除其他 Mod，也不会自动恢复备份。

## 九、首次验收清单

1. 新建电脑端实例，验证推荐窗口、全选、单选互斥和一键取消。
2. 取消已安装推荐项，确认文件在 `.modsync/backups`。
3. 不选任何推荐项，确认仍能启动。
4. 用 PojavLauncher、MCinaBox、FCL 或 Zalith Launcher 2 验证手机端无窗口且同版本不二次下载。
5. 删除手机推荐 JAR，确认日志给出手动 URL/SHA256 而不是自动恢复。
6. 提高 `catalog-version`，确认电脑端重新询问、手机端新批次自动处理，并出现版本更新日志。
7. 破坏一个必须 JAR 或让清单不可访问，确认 `STARTUP_BLOCKED`、退出码 `0`、Minecraft 主类未运行。
8. 用真实 1.6.x/1.7 JAR 验证旧电脑/手机 URL -> 仅升级组件 `mods.txt` -> 配置引导 JAR -> 合并 `mods-v4.txt` -> 完整模组重下的两至三次启动链路。
