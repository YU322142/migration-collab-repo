# MCSync 2.0 完整功能与验收合同

本文是 MCSync 2.0 的实现边界和完成判据。历史 MCModSync 文档仅用于兼容性参考；发生冲突时以本文和自动化测试为准。

## 1. 产品与兼容身份

- 产品名、发布器、界面、日志和新制品名使用 **MCSync**。
- 主版本为 `2.0.0`，技术 `modId=mcmodsync`、Java 包和旧引导入口暂时保留。
- 任意受支持的 1.9.x 客户端必须能通过旧 v2 网关升级到 MCSync 2.0。
- 继续读取 `modsync.properties`、`.modsync/` 和固定名 `MCModSync-Config.jar`；可增加新别名，但不能先删除旧入口。
- `java -jar MCSync-2.0.0.jar` 必须打开发布工作台，命令行发布能力继续可用。

## 2. 启动与生命周期

- 每次启动自动检查，不要求玩家手动点击更新。
- 检查、下载、校验和配置事务必须在 NeoForge 消费目标 Mod/配置之前完成。
- 游戏进入主菜单后不再后台下载或替换玩法内容。
- 可以在 Minecraft 窗口中显示检查和下载进度，不创建额外的可见更新器窗口。
- Mod、KubeJS、注册表资源和启动期配置发生变化时必须重启；界面不得把它描述成热更新。
- 被 Windows/Java 占用的文件由隐藏 helper 在当前 JVM 退出后原子替换，随后由启动器或显式重启流程再次启动。
- helper、主模组和发布器共享同一事务协议，不能各自维护互不兼容的状态格式。

## 3. v5 发布模型

- 结构化 JSON，`schema=5`。
- 每次发布有不可变 `releaseId` 和严格递增 `releaseSequence`。
- 相同序号只允许同一发布 ID 与同一清单 SHA256 幂等重放。
- 低序号、同序号分叉、重复键、未知枚举、路径逃逸、重复路径和不完整操作全部 fail-closed。
- 本地最高序号只在整次事务成功后提交；下载或应用失败不能提前抬高状态。
- 回滚使用事务回执恢复前像，不通过发布更低序号清单实现。

## 4. 文件下载来源与许可

来源选择按文件类别隔离：只有直接位于 `mods/` 的 Mod JAR 可以使用模组站或上游来源。发布器必须先按文件哈希自动匹配 Modrinth，再按 CurseForge fingerprint 自动匹配；都无法精确匹配时生成本地托管条目。其他文件不得查询或引用模组站，只能作为本地发布文件。

导入既有 v5 模组目录时，当前 JAR 的 SHA-256 是首要身份。唯一 `modId` 只允许作为版本升级后的名称、描述和必选状态继承线索；文件名和展示名称不得用于认定上游文件。继承结束后必须用当前 JAR 的 SHA-512/CurseForge fingerprint 重新查询来源，不能沿用旧版本的下载坐标。

Mod 文件可使用：

- `publisher-hosted`：手工适配、自制兼容层及其他确认允许再分发的文件。
- `direct`：作者或项目提供的固定 HTTPS 文件地址。
- `modrinth`：固定 project ID、version ID 和文件名。
- `curseforge`：固定 mod ID、file ID 和文件名。
- `manual`：保留给导入旧项目的兼容 schema；GUI 自动流程不会为新文件生成该来源。

分发策略：

- `redistributable`：允许由发布者托管。
- `upstream-only`：禁止复制到发布者目录，只能从上游或第三方传输代理取得。
- `manual`：只能与手动来源配合。

Modrinth/CurseForge 不取“最新版”，只解析清单锁定的版本/文件。CurseForge API key 只能存在于发布者本机或受控解析服务，不进入远程清单、客户端配置或日志。

中国区支持 MCIMirror API 预设。官方和第三方镜像都是传输候选，不是完整性信任根；无论来源如何，文件名、固定平台 ID、大小和 SHA256 必须全部符合清单。第三方端点必须显式标记 `role=mirror`、`thirdParty=true`，失败后回退其他候选。

客户端文件下载默认并发为 128，且实际工作线程数取 `min(待下载文件数, 配置并发)`。`mcsync.downloadThreads` 只允许 1–128；平台元数据识别必须使用批量 API，与文件下载并发解耦。

## 5. 同步范围

### 5.1 始终可受管

- `mods/**`，MCSync 本体走独立自更新子事务。
- 经批准的 `resourcepacks/**`、`shaderpacks/**`。
- `kubejs/startup_scripts/**`、`server_scripts/**`、`client_scripts/**`、`data/**`、`assets/**`。
- 经批准的 `kubejs/config/client.json` 与 `common.json`。
- 玩法相关 `config/**`、`defaultconfigs/**` 和 `config/ftbquests/quests/**` 白名单。
- 外置第三方 TACZ 枪包、TLM 自定义模型包、外置 Patchouli 书籍和明确的教程蓝图。
- `servers.dat` 使用结构化合并/所有权账本，不做普通文件覆盖。

### 5.2 只在首装写入

- `options.txt`。
- 实例图标和启动器元数据。
- 有实际内容的 `configureddefaults/**`。

首装文件存在后默认保持玩家版本，除非未来发布显式的、带前像约束的迁移操作。

### 5.3 模组内置内容排除

- TACZ JAR 自带的默认枪包。
- Touhou Little Maid JAR 自带的默认模型包。
- 模组 JAR 内部资源包、Patchouli 书籍、`assets/` 和 `data/`。

排除必须精确到已验证的默认子包，不能排除整个 `tacz/` 或 `tlm_custom_pack/`，以免漏掉整合包自己的内容。

### 5.4 永远不管理

- `saves/`、世界、区块、实体、POI、玩家数据、统计、进度和 gamerule。
- Xaero/JourneyMap 探索数据、路径点、截图、画作缓存和皮肤缓存。
- 日志、崩溃报告、备份、下载缓存、原生库、Mixin 导出和各类运行态缓存。
- token、密码、Web auth、用户身份缓存和语音玩家音量等隐私状态。
- 未经白名单批准的任意文件和符号链接/联接目标。

## 6. 配置键级 OTA

支持三种操作：

- `config-set`：修改单一结构化键。
- `config-merge`：合并受控对象或数组。
- `file-replace`：仅用于脚本、数据 JSON、任务章节或无法安全结构化编辑且有旧 SHA 约束的文件。

配置操作声明：路径、格式、键、值类型、允许旧值、目标值、缺失策略、冲突策略、适用 side、应用 phase、重启要求和所属发布序号。

`file-replace` 另外必须声明 `expectedSha256`（或明确的 `absent`），事务提交前会校验文件前像；没有前像约束的整文件替换一律拒绝。

首批结构化编辑器支持 TOML、严格 JSON 与 properties。JSON5、SNBT 或其他不能可靠保留类型/语义的格式在拥有专用解析器前只能使用带旧 SHA 的 `file-replace`，不能以文本搜索替换冒充键级更新。

含认证字段的文件默认禁止整文件托管。未列入操作的键应保持原值；TOML/properties 尽可能保留注释和原始排版。当前值不在 `expected` 中时默认阻断，不静默覆盖。

配置键名包含 token、password、secret、credential、API key、private key 等凭据语义时禁止 OTA；发布器也会拒绝把疑似凭据配置整文件复制进发布目录。

## 7. 原子事务与恢复

一次 OTA 的文件、目录包、配置和 MCSync 自更新属于同一发布事务：

1. 获取并严格解析清单。
2. 执行防降级和兼容版本检查。
3. 解析所有下载源，计算完整计划。
4. 将全部文件下载到同卷暂存区并校验大小/SHA256。
5. 在副本上应用配置操作并重新解析验证。
6. 再次检查目标前像、路径、文件所有权和进程状态。
7. 保存前像和事务回执。
8. 原子提交全部目标；任一失败恢复全部已提交目标。
9. 重新扫描最终状态。
10. 最后提交发布序号和成功回执。

崩溃恢复必须能识别“已暂存未提交”“部分提交”“已提交未写最终状态”，并选择继续验证或按回执回滚。不能仅依赖日志人工猜测。

## 8. 发布工作台 UI

JAR 发布工作台至少包含以下工作区：

1. 发布项目：目标 Minecraft/loader、release ID/sequence、基础 URL、输出目录。
2. 文件与来源：必需/推荐、目标路径、来源类型、许可策略、平台 ID、官方/镜像候选。
3. 内容范围：KubeJS/config/defaultconfigs/资源包/自定义内容白名单和排除原因。
4. 配置操作：键级 OTA 编辑、类型检查、旧值/冲突策略预览。
5. 验证与导出：依赖/重复 modId、许可冲突、路径安全、哈希、旧客户端升级网关和原子发布顺序。

发布器必须阻止：不允许再分发的文件进入发布目录、必须文件使用 manual、未锁版本的平台来源、凭据写入清单、重复目标路径、低 releaseSequence 和引用不存在制品的清单。

## 9. 客户端 UI

- NeoForge 使用游戏窗口内状态组件显示：检查清单、解析来源、下载、校验、暂存、等待重启、错误。
- UI 只消费核心状态事件，不自行修改文件。
- 无图形环境、Fabric preLaunch 或 UI 初始化失败时回退日志和 `.modsync/ui-status.json`，同步安全语义不变。
- 玩家可看到当前文件、总体进度、下载来源类别和是否需要重启；token、完整本地路径和敏感 URL 参数不得显示。
